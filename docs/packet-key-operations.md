# Emergency Packet v2 の鍵の運用

T-Beam(送信機)ごとの HMAC 鍵を、発行・設定・登録・更新・無効化する手順です。Packet の仕様は [`docs/emergency-packet-v2.md`](emergency-packet-v2.md) を正とします。

この文書には、コードで確かめたことだけを書いています。確かめていないことは「未確認」、作っていないものは「未実装(将来拡張)」と書いています。

- **実物の鍵を、リポジトリ・チャット・チケット・スクリーンショット・ログに載せないでください**。この文書の例も、すべて `<...>` の置き換えです
- 鍵は**端末ごとに別**です。同じ鍵を複数の端末で使わないでください

## 鍵の発行

鍵は **32バイトの乱数(16進で64文字)** です。サーバーは32バイト以外の鍵をエラーにします(`backend/app/packet_keys.py` の `KEY_BYTES = 32`)。

```sh
# OpenSSL(Git Bash、macOS、Linux)
openssl rand -hex 32
```

```powershell
# Windows PowerShell 5.1 以降
$b = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
($b | ForEach-Object { $_.ToString('x2') }) -join ''
```

- どちらも、暗号学的に安全な乱数で、16進64文字を出力します(長さと文字の種類は確認済み)
- 出力した鍵は、画面に残さず、すぐに暗号化した保管場所(パスワードマネージャーなど)へ移してください。ターミナルの履歴やログに残る場合は消してください

## 端末への設定

- T-Beam の USB シリアルで `SET key_id <英大文字の16進2文字>` と `SET key <鍵の16進64文字>` を送ります(ほかの設定項目も含めた手順は、T-Beam のファームの PR(PR #2)の `docs/tbeam-provisioning.md`)
- **`docs/tbeam-provisioning.md` は PR #2 のブランチ(`feature/firmware-v2`)にあり、まだ main にありません**
- PR #2 のファームは、32バイト以外の鍵を `SET key` で保存しません。NVS に保存済みの鍵が32バイトでない場合は送信しません(PR #2 の `hardware/TBeamEmergencySender/device_settings.h`)
- 端末の `device_id` と `key_id` は、サーバーの台帳と同じにします

## サーバーの台帳への登録

台帳の形式は `device_id → {key_id: 鍵}` の JSON です。

```json
{"TB001": {"01": "<鍵の16進64文字>"}, "TB002": {"01": "<鍵の16進64文字>"}}
```

| 方法 | 内容 | 変更の反映 |
|---|---|---|
| `PACKET_DEVICE_KEYS` | 台帳の JSON を環境変数に入れる | 環境変数なので、**プロセス(コンテナ)の再起動が必要** |
| `PACKET_DEVICE_KEYS_FILE` | 台帳の JSON ファイルのパス | ファイルは受信のたびに読み直すので、**書き換えれば再起動なしで次の受信から反映** |

- 2つを同時に指定するとエラーです
- 反映のタイミングは、コードで確かめています。台帳は、v2 の Packet を受信するたびに `load_device_key_registry()` で読み直しています(`backend/app/main.py`)。同じプロセスのままファイルを書き換えて、次の読み込みで新しい key_id が使えることも確認しました
- 台帳の形式が不正(JSON でない、device_id や key_id の形式が違う、鍵が32バイトでない)な場合は、起動時にエラーになります。実行中に不正になった場合は、v2 の Packet が 503 になります
- 起動時のログに、台帳の端末数・鍵の数・無効化した端末の数を出します(鍵の値は出しません)。台帳が空なら WARNING です

**台帳ファイルの扱い**
- ファイルには全端末の鍵が入ります。サーバーのプロセスだけが読めるようにしてください(Linux なら所有者だけが読める `600` など)
- リポジトリの中に置かないでください(`.gitignore` は `.env` と `.env.*` を除外していますが、台帳ファイルの名前は除外していません)
- バックアップを取る場合は、暗号化して保管してください

## 鍵の更新(key_id の切り替え)

台帳は、1つの `device_id` に複数の `key_id` を持てます(`{"TB001": {"01": "<旧>", "02": "<新>"}}`。コードと動作で確認済み)。受信した Packet の `key_id` で鍵を選ぶので、更新の途中でも、古い鍵と新しい鍵の両方の Packet を検証できます。

1. 新しい鍵を発行する(上記)
2. サーバーの台帳に、新しい `key_id` で新しい鍵を**追加**する(古い `key_id` は残す)
3. 端末に `SET key_id <新しい key_id>` と `SET key <新しい鍵>` を送る
4. その端末の報告が、新しい `key_id` で受理されることを確認する(`emergency_packets.key_id`)
5. 古い `key_id` の Packet が届かなくなったことを確認してから、台帳から古い `key_id` を消す

- 端末の中で、通し番号(sequence)と install_id は鍵の更新では変わりません(PR #2 のファーム)
- 鍵の有効期限や、決まった間隔での更新は、**未実装(将来拡張)**です

## 端末の紛失・盗難時の無効化

`PACKET_DISABLED_DEVICES` に、無効化する `device_id` をカンマ区切りで入れます。

- 無効化した端末の Packet は 403 `PACKET_AUTH_FAILED` になり、監査ログ(`packet_security_events`)の理由が `DEVICE_DISABLED` になります
- **`PACKET_DISABLED_DEVICES` は環境変数なので、変更を反映するにはプロセス(コンテナ)の再起動が必要です**(受信のたびに環境変数を読みますが、動いているプロセスの環境変数は外から書き換えられません)

### 再起動なしで止めたいとき

`PACKET_DEVICE_KEYS_FILE`(台帳ファイル)を使っている場合は、ファイルから消すだけで、**再起動なしで次の受信から**認証が失敗します(403 `PACKET_AUTH_FAILED`)。

| 台帳ファイルから消すもの | 止まるもの | 監査ログの理由 |
|---|---|---|
| その端末の特定の `key_id` | その `key_id` で署名した Packet だけ(ほかの `key_id` は受理されたまま) | `UNKNOWN_KEY_ID` |
| その端末(`device_id`)ごと | その端末のすべての Packet | `UNKNOWN_DEVICE` |

- 実際に動かして確かめています: 同じプロセスのまま台帳ファイルを書き換えると、消した `key_id` の Packet は次の受信から 403 になり、残した `key_id` は 201 のままでした。端末ごと消した場合も、次の受信から 403 になりました
- `PACKET_DISABLED_DEVICES`(環境変数)で無効化する方法との違い: 環境変数は再起動が必要ですが、監査ログの理由が `DEVICE_DISABLED` になり、「無効化した」ことが記録に残ります。急ぐときは台帳ファイルから消して止め、あとで `PACKET_DISABLED_DEVICES` にも入れて再起動する、という順でも構いません
- `PACKET_DEVICE_KEYS`(環境変数の台帳)を使っている場合は、どちらの方法でも再起動が必要です
- 無効化した端末を再び使う場合は、**新しい鍵**を発行して設定し直してください(紛失中に鍵が読まれた可能性があるため)

## ハブPC(ローカルサーバー)の紛失

- ハブPCには、台帳(全端末の鍵)と、ゲートウェイのキュー(署名つきの Packet)が保存されています
- ハブPCを紛失した場合は、**全端末の鍵が流出したとみなして、全端末の鍵を入れ替えてください**(新しい鍵を発行し、新しいサーバーの台帳と各端末に設定する)
- ディスクの暗号化(BitLocker など)と OS のログインを設定しておくと、流出の可能性を下げられます(推奨。設定されているかは、この文書では確認していません)

## T-Beam の限界

- PR #2 のファームは、鍵を ESP32 の NVS に、ふつうの `Preferences` で保存しています(`hardware/TBeamEmergencySender/device_settings.h`)。**NVS の暗号化やフラッシュの暗号化を有効にする設定は、ファームのコードの中にはありません**(パーティション表、sdkconfig、`nvs_flash_secure_init` などは無い)
- そのため、**物理的に端末を手にした人が、フラッシュを読み出して鍵を読める可能性があります**。端末を紛失・盗難したら、上の手順で無効化してください
- ボードの eFuse でフラッシュの暗号化を有効にしているかは、コードからは分からないので**未確認**です
- NVS の暗号化への対応は、**未実装(将来拡張)**です

## 本番での鍵の配布

- 本番のデプロイ設定(`.github/workflows/deploy-production.yml` と `infra/terraform/main.tf`)は、端末台帳(`PACKET_DEVICE_KEYS` / `PACKET_DEVICE_KEYS_FILE`)をコンテナに渡していません
- SSM Parameter Store などでの台帳の配布は、**未実装(将来拡張)**です。本番の運用を再開するときに、デプロイ設定に足す必要があります(`docs/emergency-packet-v2.md` の「v1からv2への移行手順と設定条件」)
