# TSUNAGU 開発引継ぎメモ

最終更新: 2026-11-25。開発とクラウド公開を休止しました。コードと検証済みバックアップは残し、AWSの有料リソースは削除しています。再開はまずローカル環境で行い、クラウドを作り直す場合は、その時点で利用期間と費用を決めてください。

## 再開時に読む順序

1. このメモで最終版と休止状態を確認する。
2. [README](../README.md)で利用場面とローカル起動方法を確認する。
3. [実行環境と復旧手順](runtime-and-recovery.md)で保存・再送、認証、プロキシ設定の条件を確認する。
4. LoRaを再開する場合は[Packet v2](emergency-packet-v2.md)、[鍵の運用](packet-key-operations.md)、[Gateway準備](lora-gateway-prep.md)を確認する。

## 最後に本番へ出した版

2026-11-23にPR [#30](https://github.com/gamutegamute/tsunagu/pull/30)をmainへマージしました。マージコミットは `5b635d9396894a1afb71aa3649c76f6ca255ae01`、ビルドしたソースは `184a43ac2c17652f2b7372e59d1793cbc5672199` です。両者のアプリ・インフラ・ツールには差分がありません。

この版には、送信前の端末保存、正しい受理結果を確認するまでの報告保持、IndexedDBの読取失敗からの回復、未来時刻の補正、古い情報の表示、担当避難所に基づくインシデント操作制御を含みます。本番では開発用ログインを無効にし、既知の開発用セッション鍵を拒否します。

前の本番版は2026年8月の版でした。古い休止・復旧記録だけを見て、その版へ戻さないでください。

## 確認済みの範囲

最終更新時にフロント130件、バックエンド198件、ツール95件のテストを確認し、本番用Dockerイメージをビルドしました。バックエンドは独立したPostgreSQL 16で検証しています。初回はComposeファイルを読むテスト1件が検証コンテナのマウント不足で失敗しましたが、必要なファイルを配置した再実行で成功しました。

本番ではDB移行、画面ファイルの版一致、`/health`、DB接続を確認する`/ready`、Googleログイン画面への遷移を確認しました。未ログインの本部APIは401、開発用ログインは404でした。自動テストの成功を、通信断時の実機運用やLoRaの現場性能の実証と読み替えないでください。

## DBとバックアップ

最後のスキーマは `0006_packet_clock_correction` です。0004で署名付きPacketと監査ログ、0005で対応申請の版管理、0006でLoRa観測の未来時刻補正と復元用の退避を追加しました。

完全休止時にはRDSから標準のPostgreSQL custom形式で `tsunagu.dump` を取り出し、転送前後のSHA256を照合しました。さらに独立したPostgreSQL 16へ `pg_restore --exit-on-error --no-owner --no-acl` で復元し、スキーマとデータ件数を確認しています。退避時点の件数は避難所3件、観測3件、非常送信Packet1件、インシデント状態0件、Packetセキュリティイベント0件です。

実行イメージのtar、Git履歴のbundle、Terraform stateの履歴、認証・秘密設定、復元確認結果も、運用者のローカル専用アーカイブへ退避しています。実行イメージのtarは再読込して版を確認済みです。秘密設定やDBを含むアーカイブはGitHubへ公開していません。再開時は管理者からこのアーカイブを受け取ってください。

AWS上のDBスナップショットから戻す以前の手順は、今回の休止後には使えません。スナップショットも保管料を止めるため削除しました。復旧元は検証済みのローカルダンプです。PCの故障に備え、アーカイブはアクセスを制限した別媒体にも保管してください。

## ローカルで開発を再開する

通常の試作はREADMEの `docker compose up --build` で再開できます。既定のAPIとDBはloopbackに限定されています。開発用ログイン・デモデータを使う構成なので、そのままインターネットへ公開しないでください。

退避した本番DBを確認する場合は、既存の開発DBを上書きせず、別名の空のPostgreSQL 16を用意してください。`tsunagu.dump` をコンテナへコピーして復元し、`alembic_version` が `0006_packet_clock_correction` であることと件数を確認します。復元済みDBに対してデモリセットを実行しないでください。保存イメージは `docker load --input application-image.tar` で読み込めます。

ローカルのGit履歴を失った場合はGitHubから取得するか、退避した `tsunagu-source.bundle` から取得できます。最終本番の基準は上記のマージコミットです。

## 本番を再構築するとき

休止時にFargate、ALBとその公開IPv4、RDS本体・自動バックアップ・手動スナップショット、ECR、CloudWatchのログ・アラーム、Terraform state用S3の全履歴とバケットを削除しました。IAM、Security Group、Cognito、SSM Standardなどの再利用できる無稼働の設定は残しています。作成済み扱いの古いTerraform stateを、そのまま現在の実リソースと見なさないでください。

1. ローカルでダンプを復元できることを再確認し、再開するコードとPostgreSQLの対応バージョンを決める。
2. state保存先を再作成し、退避したstateと残存リソースを照合する。通常の`apply`より先に計画を確認する。
3. ECRと非公開DBなどの基盤を作り、DBへ論理バックアップを復元する。アプリを公開する前に移行版と件数を確認する。
4. 秘密設定、許可アカウント、担当避難所、実際のALB接続元CIDRを設定してアプリを作成する。秘密設定はチャットやリポジトリへ貼らない。
5. 新ALBに合わせてDNSと証明書・Host header条件を確認する。旧ALB名は再利用しない。認証コールバックも公開URLに合わせる。
6. health、ready、本人によるログイン、担当内外の操作、端末保存・再送を確認する。

自動デプロイを止めるため、AWSのデプロイロールは明示Denyに戻しています。許可を戻すのは再構築の計画を確認した後です。また、このリポジトリの既存デプロイworkflowには旧リポジトリ向けの条件が残っています。新リポジトリへCI/CDを移す場合は、OIDCの対象とproduction環境、担当割当・プロキシの変数を合わせて修正してください。

## 残っている運用判断

最後の本番では、本部3アカウントに全避難所の担当を設定しました。現場2アカウントは、ユーザー指定により未割当です。インシデントの対応申請を使う前に、メールアドレスと担当避難所を明示して設定してください。担当外の操作はAPIでも拒否します。

署名付きLoRa Packetを実機で運用する場合は、端末台帳と鍵の配布・失効、Gateway側の設定を確認してください。開発用ダミー鍵や署名なしv1の許可を本番の既定値として使わないでください。

共有ドメインの登録・更新契約はAWSの稼働費用とは別です。このプロジェクトの休止を理由に、他の用途でも使うドメイン全体を解約しないでください。古い公開URLは休止後にはサービスを提供しません。
